### Implemented file flow and boundaries

For a new contributor: edit the ordinary TypeScript initializer, run the generator, and review the generated script text. The small `ThemeBootstrapScript` component inserts that text inline in the server layout. The initializer applies appearance once and finishes; ThemeService then owns user selections, system changes, subscriptions and cleanup.

- `frontend/infrastructure/theme/themeBootstrap.ts` is the one maintained entry. It reuses `isTheme`, `THEME_VALUES` indirectly through validation, and the shared `THEME_STORAGE_KEY`. The build-only constant selects its entry invocation; ordinary imports, typechecking and server rendering do not execute it.
- `frontend/application/providers/ThemeBootstrapScript.tsx` sits at the established startup composition boundary. It imports generated data only. The layout remains a Server Component; fonts, metadata, language/class/body attributes, ServiceProvider and the existing root hydration suppression are preserved.
- `scripts/build-theme-bootstrap.mjs` uses public esbuild 0.28.2 APIs. It emits an ES2017 browser IIFE with no unresolved imports/require, Node APIs, React, game runtime, build dependency or runtime eval. It compiles before writing, replaces output atomically, reports failures and leaves identical output untouched. Check mode never writes. Watch mode follows imported sources and disposes on Ctrl-C/SIGTERM.
- `frontend/generated/theme-bootstrap.ts` is tracked generated data. Root lint/test/coverage and CI check freshness before frontend generation can mask drift. Frontend dev/build generate initially; editing startup/shared sources additionally requires `pnpm watch:theme-bootstrap`. Storybook does not render the root layout and needs no added bootstrap prerequisite. Its existing build passed.
- `frontend/domain/theme/Theme.ts` exports the existing storage key once. `ThemeService.ts` changes only its key import; its public API, lifecycle and selected/resolved contract are unchanged. DOMAdapter narrowly catches unavailable/throwing media-query access for bootstrap and runtime handoff. LocalStorageAdapter is reused unchanged. No generic settings API or new service exists.
- Missing/invalid selection normalizes to System after application. Storage access/read/write failures are independently contained. Explicit selections never query OS during bootstrap; failed/absent media access resolves default. Default removes only `data-theme`; DOM application errors are not indiscriminately swallowed.

The initial package-add operation proposed unrelated lockfile churn; it was removed before final validation. Final lockfile impact is exactly the three-line root esbuild importer entry. All existing package resolutions remain unchanged. A subsequent frozen install and disposable offline frozen install passed. Existing installation warnings about ignored esbuild lifecycle scripts and the Storybook-design-token peer range remain visible; the installed platform binary built successfully without changing build-script permissions.

### Timing, payload and security evidence

The unchanged Next `beforeInteractive` queue ran before provider hydration on the real production home route. The test observes native insertion completion synchronously, checks the theme and exactly one storage read (two access attempts for blocked getter normalization), and sees no pressed runtime control. It leaves Next chunks operational. With only this script disabled, the same early assertion fails: `theme=null`, zero reads and zero pressed controls. ThemeService later applies dark and activates its control. Thus eventual hydration cannot make the early check falsely pass.

The inspected filmstrip shows default content then dark content (`cold-frame-1.jpeg`, `cold-frame-2.jpeg`). This is a limitation of the preserved delivery strategy, not universal flash prevention. No strategy change was made or claimed approved. A stronger first-paint requirement would need a separately reviewed delivery change; owner Codex, discuss during Sites/Dimi acceptance before any such implementation.

Generated executable payload: **1,212 bytes**, versus the legacy interpolated payload's **1,320 bytes**; gzip **539 vs 433 bytes**. The old logic minified alone would be 476 bytes, so adapter reuse/hardening has a real compressed cost despite fewer raw bytes. The small cost preserves existing tested adapters rather than introducing duplicate storage/browser boundaries. The generated TS data file is 1,354 bytes. No runtime package is added.

The generator uses deliberate string-data serialization plus esbuild's inline-script escaping. A representative source literal containing `</script><script>…`, comment syntax, Unicode line separators and ampersands survives with the correct string value, exactly one script element and no injected execution. Production HTML's queued children match the generated payload exactly. No user-controlled executable interpolation, secrets, runtime filesystem reads, eval/new Function, private compiler dependency or external script request is introduced.
